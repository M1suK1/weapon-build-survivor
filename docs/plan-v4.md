## 1. 控制台

### 1.1 交互
- 开关：`` ` ``（`KEY_QUOTELEFT`）或 `F1`。打开时 `get_tree().paused = true`，输入焦点交给输入框；`ESC` 关闭。
- 布局：屏幕下 45%，半透明深色底（`Color(0.04,0.05,0.08,0.92)`），左侧竖线；上部输出区（`RichTextLabel`，保留最近 200 行，可滚动），底部一行输入框（`LineEdit`，占位提示 `输入 help 查看命令`）。
- 历史：`↑`/`↓` 翻最近 50 条；`Tab` 补全命令名与模块 id；输入时下方显示匹配的命令提示。
- 打开控制台时：暂停原因记为 `console`，关闭时只解除这一个原因（见 1.4）。

### 1.2 命令表（最终范围，14 条）

> 原稿写「13 条」是数错了，表里实际是 14 条。**这张表就是最终范围**，不再加 `drop`/`skip`/`plan`。

| 命令 | 参数 | 作用 |
| --- | --- | --- |
| `help` | `[命令]` | 列出全部命令 / 单条详细用法 |
| `speed` | `<倍率>` | `Engine.time_scale`，0.25–8；`speed 1` 复原。倍速 ≠1 时 HUD 右上角常驻 `×N` |
| `level` | `<n>` 或 `+n` | 直接设等级 / 加 n 级（**不扣材料**；复用 `try_level` 的升级路径，见下） |
| `wave` | `<n>` | 跳到第 n 波（触发 `_on_wave_start()`） |
| `weapon` | `<id> [品质1-5]` | 获得指定武器并选中；id 见 `docs/reference.md` §1（pistol/smg/shotgun/sniper/laser/beam/grenade/blade） |
| `give` | `<模块id> <数量>` | 往库存加模块 |
| `device` | `[台数]` | 免费造装置（默认 1 台） |
| `god` | — | 无敌开关（HUD 显示 `GOD`） |
| `hp` | `<数值>` | 设置当前 HP |
| `kill` | — | 清空场上敌人（不计击杀、不掉落） |
| `spawn` | `<种类> <数量>` | 在屏外生成指定敌人（flood/runner/rock/shooter/charger） |
| `fps` | — | 切换 F3 调试面板 |
| `restart` | — | 重开一局 |
| `clear` | — | 清空输出区 |

- 未知命令：红字 + 「你是不是想输入 xxx」（编辑距离 ≤2 提示）。
- 参数错误：黄字给出该命令的用法，不执行。
- 所有命令执行后把一条 `> 输入` + 结果写进输出区；执行失败也给明确原因（例如 `weapon` 时背包已满 → 提示先丢武器）。
- 批量写法：支持一次多命令用 `;` 分隔（`god; speed 4; level 20`）。
- `level` 命令不能直接调 `try_level()`（那个函数会先扣材料，`_inv_total() < cost` 直接 return false），所以先把 `try_level()` 拆成两半：`_gain_level()`（`level += 1` + `_roll_offer()` + `_open_pick()`）和 `try_level()`（查材料 → 扣材料 → 调 `_gain_level()`）。命令调 `_gain_level()`，`+n` 连升就连续弹 n 次四选一，不做批量跳过。

### 1.3 与现有作弊/自测的关系
- **删掉** F5–F9 热键（全部并入控制台命令）。
- **保留** CLI 参数 `cheat=...`（无头自测没有控制台，机器人还是要用），但实现改为调用同一套命令函数，避免两套逻辑。
- 控制台命令与 CLI 共用一个 `_cmd_<name>(args) -> String`（返回一行结果或错误），控制台只负责解析与显示。

### 1.4 暂停原因改成集合（顺手修一个真 bug）
现在 `_close_pick()` 无条件 `get_tree().paused = false`：如果选卡时打开控制台、再关控制台，会把选卡的暂停一起解除（敌人复活）。
改成：`var pause_reasons := {}`，`_set_pause(key: String, on: bool)` 增删集合，`get_tree().paused = not pause_reasons.is_empty()`。三个来源：`build` / `pick` / `console`。

### 1.5 验收
- 打开控制台 → 敌人在原地不动；关闭 → 继续动。
- `speed 4` 后 HUD 显示 `×4`，`speed 1` 恢复。
- `weapon sniper 5` → 左栏出现金色狙击枪并被选中。
- 边开选卡边开控制台，关控制台后仍停在选卡界面（暂停没有被误解除）。
- `level 20` 会弹选卡（不是静默加等级）。

## 3. 删掉 bulwark，改成「重装变种」

### 3.1 删除清单
- `scripts/data/enemies_db.gd`：`ENEMY_KINDS["bulwark"]`。
- `scripts/game.gd`：`bulwark_t` / `last_move_dir` / `prev_ppos` / `_tick_bulwark()` / `_spawn_bulwark_arc()` / `_count_bulwark()` / `_recycle_bulwark()`、`_pt_log` 里的 `bw=`。
- `scripts/enemy.gd`：`bulwark` 的菱形绘制分支、`telegraph` 的方块预兆（`telegraph` 字段本身保留给精英冲刺用）。

### 3.2 新机制：变种标记 `variant`
不给新种类，而是给现有种类打标记：`e.variant = "brute"`（内部名），视觉基于原种类派生，数值只动血量。

| 属性 | 规则 |
| --- | --- |
| 模板 | 白名单：`flood`（100）/ `rock`（52）/ `shooter`（70）。`runner`（205）与 `charger`（78，冲刺 780）**不进池** → 从源头不会生成高速重装 |
| 兜底 | 生成时再检查一次 `speed > 120` 就换模板，防以后改表把高速怪放进白名单 |
| 血量 | `base_hp × 8`（8 倍）。按 wave 12 的中等 build 估，大约要 5–8 发 |
| 速度 | **不改**，用模板原速（这就是「不要改速度」）；不加速、不减速 |
| 半径 | **不改**，和模板一致（碰撞手感不动；只靠颜色区分，不靠变大） |
| 颜色 | 原色 `.lerp(Color(0.72, 0.22, 0.42), 0.55)` + 外圈 2px 高亮描边（和普通怪一眼分开） |
| 伤害 | 接触伤害不变（靠数量和拦路施压，不靠单只秒人） |

### 3.3 「至少 5 次攻击」怎么保证
玩家的单发伤害跨度能到几十倍，纯按血量算不出次数。所以加一条硬规则：

**单发伤害上限**：`e.hit_cap = e.max_hp * 0.20`（任何一次命中最多打掉 20% 血）。

- 这是**规则**，不是基础数值：它不改 3.2 表里的血量/速度/半径，只保证击杀下限 5 发。
- 只对 `variant == "brute"` 生效；普通怪不受影响。
- 与现有机制不冲突：穿透/溅射对**不同**目标照常结算；同一个目标一次开火只结算一次。
- HUD/调试面板显示 `hit_cap`，方便以后调。
- 副作用（已知）：这类怪对「高单发低射速」的狙击枪不友好，对「高频」的冲锋枪/镭射友好 —— **这是有意的**，正好把武器选择逼出差异。

### 3.4 生成
- 触发：wave ≥ 3 起，每 20 秒一波。
- 数量：每波 2–4 只；同屏上限 **50**（用户指定，和 §4 的 400 总上限是两回事）。
- 位置：**屏幕外**（复用 `SPAWN_R_MIN..MAX` = 1220–1400 的随机角度）。
- 行为：直线走向玩家（模板原速），不追击走位、不回收 —— 清不掉就会持续堆成包围圈，逼玩家换位置。
- HUD：状态栏出现 `重装 N`（当前同屏数量），超过 30 只变红。

### 3.5 验收
- 场上不再出现菱形 bulwark；出现的变种是变色 + 2px 描边，**速度和半径与模板一致**（不更快、不变大）。
- 生成日志里 brute 的模板只会是 flood/rock/shooter，`speed` ≤ 100。
- 用 `boardtest`/作弊码把单发伤害调到 10 倍，变种仍然需要 ≥5 发（验证 hit_cap）。
- 30 分钟后同屏变种不超过 50。

## 4. 敌人 >300 的帧率问题

### 4.1 先测量（P0，不要凭感觉改）
F3 面板拆成四段计时：`ai_ms`（敌人 `_physics_process` 合计）/ `draw_ms`（所有 `_draw`）/ `combat_ms`（开火 + 接触）/ `other_ms`，用 `Time.get_ticks_usec()` 包住。跑 `cheat=wave=25` 拉到 300/400 只，记录四项占比再决定动哪里。

预期（待实测确认）：`draw_ms` 占大头 —— 每只敌人都是独立 `Node2D` 且**每帧无条件 `queue_redraw()`**，每只画 3–5 个图元（身体 + 描边 + 血条 + 冲刺线），300 只就是每帧上千次 draw call。

### 4.2 优化（按预期收益排序，逐条可独立验证）

**A. 集中渲染（最大头）**
- 新增 `scripts/enemy_renderer.gd`（一个 `Node2D`），在它的 `_draw()` 里遍历敌人数组，用 `draw_circle` / `draw_colored_polygon` / `draw_line` 一次性画完所有敌人与血条。
- 敌人节点关掉自己的 `_draw`（`set_process(false)` + 不 `queue_redraw`），只保留逻辑。
- 收益：draw call 从 ~1500 降到个位数；敌人节点不再各自维护 CanvasItem。
- 风险：颜色/形状要在渲染器里复刻（`enemy.gd` 里的绘制分支搬过去），视觉要逐个比对截图。

**B. 屏幕外降频**
- 距离玩家 > 1600 的敌人每 4 帧更新一次 AI（用 `Engine.get_physics_frames() % 4 == i % 4` 分桶，避免同一帧全更新）。
- 收益：400 只里通常一半在屏外，AI 开销直接砍半。

**C. 查询走空间网格**
- `_contact()` 与 `_targets_in_range()` 现在每帧遍历全部敌人（多武器时是 武器数 × 敌人数）。改成 64px 网格：每 6 帧重建一次 `cell -> [enemy]`，查询只看玩家/武器范围内的 3×3 / N×N 格。
- 收益：`combat_ms` 从 O(武器×敌人) 降到 O(局部)。

**D. 减少每帧分配**
- `get_tree().get_nodes_in_group("enemy")` 每帧返回新数组 → 改成维护 `var enemies: Array`（生成/死亡时增删）。
- `_count_kind()` / `_count_bulwark()` 之类每次遍历 → 用计数器维护。

**E. 同屏上限直接降到 400**
- `MAX_ENEMIES := 400`（`scripts/data/enemies_db.gd:21`，改前 560）。
- **不做**帧率自适应、不做「560→400」两段式、不加降级状态机 —— 用户要的是直接 400，HUD 的 `上限` 自动跟常量走。
- 理由：少一套会抖动的降级逻辑；优化目标也按 400 验收。

### 4.3 验收
- 300 只：≥55 FPS（1440p，本机 RTX 3070 Ti）。
- 400 只：≥45 FPS。
- `draw_ms` 从（测得值）降到 ≤4ms。
- 若 400 只达不到 45 FPS：先做完 A–D 再复测，**不回头改上限**。

## 5. 波次多样性

### 5.1 现状问题
`WAVE_PLANS` 是 5 个「单一主题」—— 涌潮只有 flood、疾行只有 runner、磐石只有 rock，玩家整波只看到一种怪。

### 5.2 改法：主题 + 陪衬 + 配额序列
- 每个编成保留主题（决定 `coeff` 总血量预算），但 `kinds` 改成「主导 + 陪衬」：

| 编成 | 主导 | 陪衬（合计占比） |
| --- | --- | --- |
| 涌潮 | flood 0.70 | runner 0.15 / shooter 0.10 / rock 0.05 |
| 疾行 | runner 0.65 | flood 0.20 / shooter 0.10 / rock 0.05 |
| 磐石 | rock 0.60 | flood 0.25 / shooter 0.10 / runner 0.05 |
| 混编 | flood 0.40 | runner 0.25 / shooter 0.20 / rock 0.15 |

- **配额序列**：每波开始时按权重生成一个长度 N（≈本波预计生成数）的种类序列，打乱但保证「每 6 只里至少 1 只不是主导」；生成时按序取。好处：小样本也不会整波只有一种，且同 seed 可复现。
- HUD 波次名改成 `波次 7 · 疾行（+混编）`。

### 5.3 验收
- 任意一波的前 20 只里，至少出现 3 种敌人（用 `_pt_log` 的 `kinds=` 统计验证）。
- 主导种类占比落在 55%–75%。

## 6. 精英冲刺方向锁定

### 6.1 现状
`_charger_step()` 在蓄力 0.9s 内每帧按玩家当前位置画红线；冲刺开始后如果方向仍在追踪，玩家永远躲不开（红线是骗人的）。

### 6.2 改法
- 蓄力开始时记 `dash_dir`，蓄力期间**跟随玩家更新**（红线始终指向玩家，作为「警告」）。
- **蓄力结束的瞬间锁定**：`dash_dir_locked = dash_dir`，并置 `e.dash_locked = true`（此后不再更新）。
- 冲刺全过程用 `dash_dir_locked`；视觉上锁定后红线变成**实线 + 端点圆点**（区别「还在瞄准」与「已经定死」）。
- 命中判定改成线段判定：玩家到冲刺线段的距离 < `玩家半径 + 敌人半径` 即命中（现在是距离采样，快冲时会穿过去）。
- 给玩家一个公平性保证：锁定到冲刺开始有 0.15s 的「预备帧」（精英原地抖动一下），这段时间足够侧移一步。

### 6.3 验收
- 客户端手动测试：看到红线变实线后直线后撤/侧移能躲开。
- `playtest` 里记录 `dash 命中/未命中` 计数写进 `[TEST]` 日志。

## 7. 合成配方改由升级奖励直出

### 7.1 现状（代码事实，改前 `bda685f`）
- 升级四选一本来就是「3 张 buff + 1 张配方卡」：`_roll_offer()`（`scripts/game.gd:2613-2634`）第 4 张调 `_roll_recipe_card()`（`2638-2656`）。
- 但这张「配方卡」**不解锁配方**，只是发 1–N 个该模块：`_take_card()` 的 `else` 分支（`3548-3549`）执行 `_add_inv(id, 1 + int(level / 12))`。卡面写的是「立刻获得 1 个（N 阶）」（`3454`）。
- 真正决定能不能合成的是等级：`recipe_state()`（`2465-2488`）里 `level < CRAFT_UNLOCK[mid]`；`CRAFT_UNLOCK` 表在 `scripts/data/modules_db.gd:49-51`（`add 4` / `amp 8` / `reson 16`，其余 5–20）。配方卡池还额外提前 3 级（`2650`：`level < CRAFT_UNLOCK - 3`）。
- 配方面板与装置配方选择器也读这个等级：`2899` / `2901`（未解锁提示）、`2997`（装置配方跳过）、`3014`。

### 7.2 新规则
1. **删等级解锁**：`CRAFT_UNLOCK` 从 `modules_db.gd` 与 `game.gd:38` 一起删；`recipe_state()` 不再看 `level`。
2. **新状态**：`var recipe_unlocked := {}`（本局内有效，`mid → true`），开局为空。没有跨局存档，不需要迁移。
3. **第 4 张卡改成解锁卡**：`_roll_recipe_card()` 只从**还没解锁**的配方里抽，沿用 bind 过滤（没有对应武器就不进池），返回 `{"kind": "recipe", "id": mid, "unlock": true}`。
4. **领取**：`_take_card()` 里 `unlock == true` → `recipe_unlocked[id] = true`，屏幕上飘一行 `解锁配方：<名>`（复用 `drag_hint`（`game.gd:215`）的样式思路，2 秒淡出）；不再发模块。
5. **池子空了**（20 个全解锁 / 没匹配武器）→ 第 4 张退化成「模块礼包」：`{"kind": "recipe", "id": "add", "unlock": false}`，保留老行为（`_add_inv`），卡面写「立刻获得」。这样四选一永远有 4 张，不会出现空位。
6. **特化配方**（`bind` 到某把武器）规则不变：拿到对应武器后才可能被抽到。
7. **`recipe_state()` 输出**：未解锁 → `"未解锁（升级时选配方卡）"`；绑定武器 / 料不够的两种状态保持不变。
8. **文案**：
   - `2899` → 「还没有解锁任何配方（升级时选第 4 张配方卡）」
   - `2901` → 「还有 %d 个配方没解锁（在升级奖励里选）」
   - `3014` → 「还没有解锁任何配方」
   - `_paint_offer()` 卡面（`3451-3455`）：解锁卡 `nm = "配方 · %s（解锁）"`、`ds = "解锁后可合成 · 需 %d 个 %d 阶料"`；礼包卡沿用「立刻获得」。
   - `_reroll_recipe()`（`3554-3574`，按 `T`）文案改成「配方卡可以按 T 换成一张 buff」，判定条件仍只认第 4 张的 `kind == "recipe"`。
9. **装置配方选择器**：`2997` 的 `level < CRAFT_UNLOCK...` 改成 `not recipe_unlocked.has(mid)`，其余（`not _has_weapon_bind`）保留。
10. **bot 自测**：现在 `pick_delay` 自动选卡永远拿第 1 张（buff），配方会一直锁着，装置自测全空转。改成：自动选卡时若 `level % 2 == 0` 且第 4 张是解锁卡，选第 4 张，否则选第 1 张（900s 内约解锁 14 个）。
11. **`_pt_log`** 加一个 `rcp=%d`（已解锁配方数），给 `[TEST] end` 做验收。

### 7.3 节奏与数值
- 每级都有一次机会拿配方卡（不额外消耗等级）；拿卡就是放弃一张 buff，这是明码的取舍。
- 20 个配方、一局约 25–30 级：每次都拿 ≈ 20 级全解锁；正常玩 ≈ 12–18 个解锁。比原来「Lv4/8/16 三档全开」慢，但**顺序由玩家定**，想先做哪条线就先拿哪张。
- 前期可能抽到高阶配方（T4 需 9 个 T3 料）= 看得见吃不着：卡面标阶数与料数，可按 `T` 换掉。
- 不再有「等级到了自动解锁」的隐性节奏；`README` 的「配方解锁 Lv4/8/16」一列改成「升级选卡解锁」。

### 7.4 兼容与测试影响
- `cheat=level` / 控制台 `level 20` 只改等级，**不再解锁配方**（行为变化，不是 bug）。要测配方：`give base 300` 后连续按 `U`，或让 bot 跑一局。
- `boardtest` 不依赖解锁状态，应该原样通过；plan-v3 V1 的 `devpick` 截图需要重拍（未解锁态现在由 `recipe_unlocked` 决定）。
- `docs/reference.md` §3.4 的「配方解锁等级」表整段删掉，改成一句「全部配方通过升级四选一的第 4 张解锁；特化配方要先有对应武器才进池」。

### 7.5 验收
- 开局（Lv1）配方面板 0 个可合成，提示「升级时选第 4 张配方卡」。
- 升到 Lv2 抽到解锁卡并选中 → 该配方立刻变「可合成（料够）」，HUD 出现解锁提示。
- 同一配方不会第二次出现（池子已排除）；全部解锁后第 4 张变模块礼包，点它加模块、不报错。
- `playtest bot pt=300`：`[TEST] end` 里 `rcp=` 随等级上升，`dev=` 不再长期 `0/0`。
- `T` 键把配方卡换成 buff 仍可用。
