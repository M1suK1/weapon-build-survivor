## 0. 先说一个查出来的真 bug

`devices[i]["kind"]` 存的是**模块 id 字符串**（`""` 表示空闲，`"add"` / `"reson"` 表示正在做什么），但面板和计数用了整数判定：

- `_rebuild_tab_device()`：`var kind := int(dv["kind"])` → `int("add") == 0` → `busy = false` → **正在合成的装置被显示成「空闲」**。
- `_busy_devices()`：`if int(d["kind"]) != 0: n += 1` → 永远不成立 → `空闲数 = 总数`。

所以装置其实一直在干活，只是界面骗人（合成日志 `c=0/16/51/17` 也证明它在产出）。
**§2 会把判定统一成「kind 是非空字符串 = 忙」，并顺手把这块的数据结构写清楚。** 我上一轮把这里从 `String(kind) != ""` 改成 `int(kind) != 0`，方向错了，这次改回来。

## 1. 鼠标拖动（替换现在的「拿起 → 点放」）

### 1.1 三个可拖的东西

| 源 | 拖出来是什么 | 松开在空格上 | 松开在已有模块的格上 | 松开在库存区 | 松开在回收区 / 屏外 |
| --- | --- | --- | --- | --- | --- |
| 库存行的模块 | 该 id 的 1 个 | 装入，并把该格**方案**写成这个 id | 交换：旧模块退回库存，新模块进入 | 无操作 | 取消 |
| 电路板上的模块 | 那一个实例 | 移动（原格留空、方案清空） | 交换两格的模块与方案 | 卸下并退回库存、清方案 | 取消 |
| 「手持」状态（旧交互） | 同库存 | 保留为无障碍备选 | 保留 | 取消手持 | 取消手持 |

### 1.2 交互细节

- **起手阈值**：按下后移动超过 **6 px** 才算拖动；没超过就松手 = 旧行为（拿起 / 装入），两种操作都留着。
- **幽灵**：一个 240×34 的半透明面板跟随鼠标（偏移 `+14, +10`），显示 `▣ 共振` + `×3`（库存剩余）。源条目变 40% 透明，不消失。
- **落点高亮**：
  - 合法格：金色 3 px 描边 + 背景提亮 8%。
  - 会替换已有模块的格：描边变橙，并在板上方浮一行 `出力 38.9 → 52.1 (+34%)`（正绿负红）。这一行用和 `_board_total()` 同一套计算，**所见即所得**。
  - 非法（拖到空白）：鼠标旁画红圈，行内提示 `放到格子上`。
- **交换预览**：拖的是已装模块时，源格画成 50% 虚线框，目标格显示交换后的出力。
- **取消**：拖拽中按 `ESC`、或松开在非法位置 → 回到原状，不改任何数据（**先算后改**，不在拖动过程中写 `slots`）。
- **坐标**：一律用 `get_global_mouse_position()`。之前踩过 `pick_root.get_global_rect()` 是 2560×1440（画布被 2× 放大），用 `event.position` 会偏。
- **暂停**：构筑屏本来就是暂停态，拖动期间不需要额外暂停。

### 1.3 实现方式（不依赖 Godot 的 `_get_drag_data`）

构筑屏的库存行和格子都是**运行时重建的 Control**，用 Godot 原生 drag&drop 需要给每个节点实现 `_get_drag_data / _can_drop_data / _drop_data`，而且原生拖拽的预览是一张纹理、做不了「出力预览」和「交换虚线框」。

所以手写一套状态机放在 `scripts/game.gd`：

```
var drag := {}            # {} = 空闲
# {"src": "inv"|"slot", "mid": String, "from": int, "start": Vector2,
#  "pos": Vector2, "active": bool}
```

- `_input(InputEventMouseButton)` 左键按下：先判断落在「库存行 / 格子 / 其它」哪一类，记下 `drag`。
- `_input(InputEventMouseMotion)`：`pos` 更新；`active = active or (pos - start).length() > 6.0`；`active` 时 `get_viewport().set_input_as_handled()`，避免格子自己的 `gui_input` 再吃一次。
- 左键松开：`active` → 走 §1.1 的表；否则走旧的点击逻辑。
- `_on_slot_input()` 开头加 `if drag.get("active", false): return`，防止双处理。

界面上要新增三个可点区域（都在 `build_root` 内）：

| 区域 | 位置 | 作用 |
| --- | --- | --- |
| 库存列表 | 右栏标签页内 | 拖动源 |
| 电路板 | 左侧 (100, 185) 起 | 落点 |
| 回收区 | 构筑屏右下角 `(1120, 640)`，56×56，`⌫` 图标 | 拖进来 = 卸下退回库存 |

### 1.4 和「槽位方案」的关系

拖动**不改规则**，只改操作手感：拖入 = 改写该格方案；拖出 = 清空该格方案；交换 = 两边方案一起换。缺料红框、自动补料、bot 的自动配置方案全部不变。

## 2. 装置指派配方（修 bug + 给入口）

### 2.1 面板重做

「装置」标签页，每台一行（高 44）：

```
装置 1   [空闲]                      [ 选配方 ▾ ]
装置 2   [合成 共振  4.2s / 18s]     [ 取消 ]
         ▓▓▓▓▓▓▓░░░░░░░░░░
```

- 点 `选配方 ▾` → 在标签页右侧弹一个 260×360 的列表（**不做成新的一级界面**，避免层级太深）：
  - 只列**当前能开始**的配方：已解锁、材料够、绑定武器的配方要求该武器在场。
  - 每行：`共振  2×增幅 · 18s  [ 开始 ]`，材料不足的行灰掉并在右侧写 `缺 增幅 ×2`。
  - 底部固定两行：`[ 自动 ]`（= 现有 `_auto_recipe()` 逻辑，勾上后该装置做完自动挑下一个）与 `[ 全部空闲装置开始 ]`。
- `[ 取消 ]` 返还已扣的材料（**全额**，不惩罚，避免玩家怕点错），装置回空闲。
- 快捷键保留：`C` = 把当前选中的配方塞进**第一台空闲**装置；`V` / `B` = 快捷增幅 / 共振（同现在）。

### 2.2 数据结构（写清楚，防止再出 §0 那种类型混乱）

```
devices[i] = {
  "kind": "",        # String："" 空闲；否则是 MODULES 里的模块 id
  "left": 0.0,       # float：剩余秒数
  "total": 0.0,      # float：总时长（进度条用）
  "auto": false,     # bool：做完自动接下一个（§2.3）
}
```

统一约定：**判忙用 `String(d["kind"]) != ""`**，判闲用 `== ""`。所有比较都走 `String()`，不再 `int()`。

### 2.3 「自动」开关顺手治经济溢出

上一轮 900 秒复测里库存堆到 **336 个基础模块**根本用不掉，原因是 3 台装置 × 每次 5 秒 ≈ 0.6 次/秒，而掉落 5–12 个/秒。

- 每台装置加 `auto`：完成时若材料还够，自动再下单同一配方；不够就按 `_auto_recipe()` 换一个能做的。
- 面板顶部显示 `装置 3 台 · 自动 2 · 空闲 1`。
- 这不能让吞吐量提高到跟上掉落，但能把「闲置的装置」变成「一直在转」，至少让堆积慢下来。真正的吞吐问题留给数值阶段（提高单次合成消耗 or 降低掉落），本方案不擅自改数值。

### 2.4 bot 兼容

- `playtest` / `bot` 模式默认把所有装置设成 `auto = true`，行为等价于现在的 `_auto_recipe()` 连续下单，平衡曲线不漂移。
- 新增 CLI `noautocraft` 把 auto 全关，便于复现「装置闲置」的场景。

## 3. 压迫型敌人：慢速高阶集群（bulwark）

### 3.1 它是什么

现有五种敌人是「速度越快血越少」的谱系（涌潮 100 / 疾行 205 / 磐石 52 / 射手 70 / 冲刺精英 78）。新敌人**故意打破这条谱系**：速度极慢，但血量远超同波次，单只就能在玩家身上压出 1.5 秒的击杀成本。

| 字段 | 值 | 说明 |
| --- | --- | --- |
| `id` | `bulwark` | 壁垒 |
| 速度 | 38 | 玩家 230，相差 6 倍 —— 永远追不上，作用不是「抓到」而是「占地方」 |
| `hp_mult` | 6.0 | 同波次涌潮的 6 倍；比冲刺精英（9.0）低，但数量多 |
| 半径 | 26 | 明显比涌潮（13）大一圈 |
| 颜色 | `#6B5B7A` 深灰紫 + 裂纹内圈 | 一眼看出「厚」 |
| 击退抗性 | 85% | 玩家击退对它几乎无效，推不动 |
| 接触伤害 | ×1.6 | 被墙压住很痛 |

### 3.2 生成规则（独立于波次预算）

生成位置是**玩家前进方向的前方**，不是背后 —— 理由记在这里，免得以后又改回去：

> bulwark 速度只有 38，生成在背后的话它永远追不上玩家；玩家只要一直朝一个方向走就能完全无视它们，等于白做一种敌人。
> 生成在前方则相反：玩家往前走会**主动撞上**这堵墙，必须**拐弯绕开**（走位）或者花时间砸开（火力）。同屏上限一到，新的墙就不再生成，于是「绕开」成为唯一可持续的解法 —— 这正是我们要的「频繁走位」。

- 起始波次：`wave >= 3`。
- 计时器：每 **16 秒** 尝试一次（与刷怪计时器分开）。
- 同屏上限：`min(14, 2 + wave / 4)`。
- 每次生成 **3–4 只**，在**玩家移动方向 ±50°**、距离 **380–460** 的扇形上排成一排（弧形栅栏），**每人间隔 0.6 秒依次出生**（排队，不是一帧全出）。
- 玩家几乎静止时（速度 < 20）：取「上一次的移动方向」；完全没有记录过就用随机角，此时改成**环绕生成**（360° 均分），避免站桩时反而没有压力。
- **出现预警**：每只出生前 **0.9 秒**先画一个半透明轮廓（色 `#6B5B7A`、alpha 0.25）+ 一圈收缩的圆环，然后实体淡入。玩家看到前方亮起一整排轮廓，就知道「这条路要被堵了」，有时间决定是绕还是打。
- **回收**：bolwark 落在玩家身后 **> 1600 px** 且超过 **6 秒** 时静默移除（不掉落、不给补偿）。理由是它们围不住玩家之后只是站在身后吃内存；1600 远大于屏幕对角（约 1184），移除瞬间看不见。
- 不消耗 `spawn_acc`，不参与 `_plan_avg_mult()` 的预算计算 —— 它是**额外压力**，不是替代。

### 3.3 为什么这样会有压迫感

- **堵的是「你正在走的方向」**：玩家习惯直线逃跑，墙从正前方出现，第一步就得改向。改向之后新的墙又出现在新的前进方向上 —— 形成「一直在拐弯」的节奏。
- **推不动**（85% 击退抗性），只能绕或砸。
- **很厚**（`hp_mult 6`），自动开火清不干净；想砸开就得停下来，而停下来会被后面的杂兵贴上 —— 这就把「走位」和「火力」变成了真取舍。
- **有预警但时间很短**（0.9 秒）：能反应，但不足以慢悠悠规划。
- **同屏上限 14** 保证压力有天花板，不会滚成必死局。

### 3.4 补偿：它们也是最肥的掉落

按现有「掉落按血量成正比」的规则（`chance = DROP_CHANCE × e.hp_mult / 平均倍率`），一只 bulwark 相当于 6 只涌潮的掉落。**高风险高回报**，玩家绕开或清掉都能接受。

### 3.5 边缘预警

**只对「在屏幕外、但正前方有墙正在生成」的情况**画提示：屏幕对应方向的边缘画一条红色半透明渐隐条（宽 6 px，透明度 0.15 → 0.35），持续到那批 bulwark 进入视野或预警结束。

配合 3.2 的 0.9 秒轮廓预兆，玩家能读到「前方要堵了」。

### 3.6 实现要点

- `scripts/enemy.gd`：`_draw()` 增加 `bulwark` 分支（六边形 + 内圈裂纹 + 受击闪白）；击退接受度按 `kind` 取系数；新增 `telegraph` 字段（0.9 → 0.0 的淡入）。
- `scripts/game.gd`：
  - `ENEMY_KINDS` 加 `"bulwark"`。
  - 新增 `var bulwark_t := 0.0`、`var bulwark_queue: Array = []`（元素 `{pos, delay}`）、`var last_move_dir := Vector2.RIGHT`，在 `_spawn()` 里推进（与普通刷怪共用函数但各自计时）。
  - `_spawn_bulwark_wave()`：按玩家当前速度方向算前方扇形、生成排队、登记预警。
  - `_recycle_bulwark()`：每 0.5 秒扫一次，回收落在身后 > 1600 且存在 > 6 秒的。
  - 边缘预警在 `_draw()` 里画。
- `MAX_ENEMIES` 560 不变，bulwark 计入其中（上限 14 只，占比很小）。

## 5. 要你拍板的三条（其余已按推荐定案）

1. **拖动要不要保留「点一下拿起、再点一下放下」？**
   推荐 **保留**：拖拽会失效的场合（触控板、远程桌面、手抖）总得有个备选，而且它已经写好了。默认两种都开。
2. **装置取消合成是否全额返还材料？**
   推荐 **全额返还**。惩罚性返还会让玩家不敢试配方，而这个游戏的信息量已经够多了。
3. **bulwark 同屏上限 14 只够不够「压迫」？**
   推荐 **先按 14 做**，用 900 秒 bot 复测看走位频率（`[TEST]` 里记录玩家位置变化总量）再决定要不要提到 20。数量越多越压迫，但也越吃帧（每只都是独立 Node2D）。

## 6. 已定案（这一轮你拍过的）

- **bulwark 生成在玩家前方堵路，不在身后**（原话：「要经常生成在前方堵路，不考虑在身后生成，本来速度就慢，全生成在后面就会导致玩家只要一直朝一个方向走就能忽略这些敌人。」）。据此把 §3.2 的策略改成「前方 ±50° 弧形栅栏 + 0.9 秒轮廓预兆 + 身后 1600px 静默回收」。
- 先前两条定案仍然有效：背包上限 6 且选完再挑一把替换、宝箱品质只由宝箱权重决定。
